## What this project is

A couples' movie recommendation app. Two people with different tastes fill out taste profiles, set tonight's mood, and Claude reasons about compatibility — producing a **taste map** (per-person analysis + overlap + tension points), a **ranked list** with match scores, and a **conversational** write-up. Plus a refinement loop (♥ keep / ✕ remove → regenerate) and a private **rough-day toggle** (one person silently deprioritizes their own preferences as an act of care).

Next.js 15 App Router + React 19 on Cloudflare Workers via OpenNext, D1 for data, Google OAuth, Anthropic structured outputs for matching, TMDB for the catalog.

**Glossary** (terms used throughout the docs and code):
- **Group** — the unit of matching. A couple is a group of 2; solo is a group of 1. There is no `couples` table by design.
- **`__solo__`** — the reserved name of the auto-created personal group backing solo mode. Hidden from group lists.
- **Full ritual** vs **quick match** — the two entry flows. Ritual edits your profile then sets mood; quick match is mood-only for an exhausted user (the "Alice after an 18-hour shift" case).
- **Round** — one matching call within a session. Capped at 10/session.
- **Titles, not movies** — the catalog table is `titles` with a `content_type` column, so TV support later isn't a rename.

Read in this order to get oriented: `CLAUDE.md` → `DESIGN.md` → `docs/plans/2026-07-18-movie-night-phase1-plan.md` (the plan, with per-phase status banners) → `dev/implementation-log.md` (the narrative record, longest but richest).

## Phase 8 bug hunt — 10 confirmed defects fixed

Four parallel hunters (holistic, multipass, differential over server; exploratory over client). Every finding was independently re-verified against the code before any fix; each fix is its own commit with a failing test first.

**The one that matters most:** a **D1 100-bound-parameter breach**. Two members' profiles union up to 200 tmdb ids into a single `IN (...)`; real D1 rejects >100, so the core match path returned a generic 500 — and it failed *for exactly the most engaged couples*, since it scales with how full your profile is. It was invisible because the fake D1 (`node:sqlite`, limit 999) happily accepted the oversized query, so the entire suite passed while production would break. Fixed by chunking (`chunk()` + `D1_IN_CHUNK_SIZE=90` in `src/lib/db.ts`), **and the fake now enforces the 100-param ceiling** so the whole class is provable in a unit test. Triple-confirmed across hunters.

Others: dead refresh path (session cookie's `Max-Age` tied to the 15m JWT meant a real browser never reached rotation — the 90-day token was inert, and existing tests masked it with a cookie pair no browser emits); solo detection disagreeing between server (group name) and client (member count); the rough-day weighting leaking the toggler through model prose; null-body 500s; a cron miscount-and-resubmit; and four client-side UX defects.

Generalizable lessons were routed to `docs/pitfalls/` — implementation **PLAT-1** (D1 param limit + chunk pattern) and testing **§7** (a fake must enforce the real dependency's limits; fixtures must reproduce states a real client actually emits).

## Operational guardrails learned here — don't rediscover these

**Verification**
- `next dev` has **no Cloudflare bindings**. A signed-in session is impossible under it. Use `npx wrangler dev` after an OpenNext build for anything binding-dependent.
- jsdom does no layout and no animation timing. Any layout or motion claim needs a real browser. Two real bugs (a `<fieldset>` forcing 435px at a 375px viewport; reduced-motion leaving whole pages invisible) were invisible to 500+ passing tests.
- **The Browser pane's screenshot can lag the DOM.** Measure with `getComputedStyle`/`getBoundingClientRect` via `javascript_tool`; treat a single screenshot as a hint, not evidence.
- Two synthetic `.click()` calls in one JS block both read pre-click props (React batches within a task). `await` between clicks — a human can't produce two clicks in one task, so this looks like a state-machine bug and isn't.

**Testing**
- jsdom has **no working `localStorage`** in this setup (the accessor exists but reads `undefined`). Inject a store or `Object.defineProperty`.
- Each `PhasedLoading` phase's timer is scheduled by the effect *after* the previous render, so `advanceTimersByTime(5000)` in one `act()` only fires the first phase. Advance one phase at a time.
- Turbopack/SWC drops the leading space in some JSXText continuations after a closing tag (`</strong> — mood` → `</strong>— mood`) while esbuild preserves it — so vitest stays green while the served HTML is wrong. Use explicit `{" — "}` for load-bearing whitespace.
- Some heavy jsdom tests sit near vitest's 5s default and pass locally but time out on CI's slower runner. Set an explicit generous timeout rather than trimming the assertion (this bit us once, on the 60-removal cap test).

**Accepted, do not re-litigate**
- Two check-then-act TOCTOU races (group-join rate limit, match round limit) are **deliberately accepted** — reasoning recorded twice, consistently, in the plan and log. The fake D1 is synchronous and cannot reproduce them anyway.
