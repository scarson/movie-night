# Movie Match — Session Handoff

**Date:** March 29, 2026
**Author:** Sam (via Claude brainstorming session)
**Artifact:** `mockup.jsx` — a working React POC (~1,038 lines) that runs as a Claude artifact with live Anthropic API calls

## What This Is

A proof-of-concept for a couples' movie recommendation app. Two people with different tastes fill out profiles, set a mood for the evening, and an AI finds movies that work for both of them. The POC proves out the core matching logic — can an LLM reason about taste compatibility and surface good compromises?

This is Sam's friend Thayne's app idea. Sam is prototyping it to demonstrate feasibility.

## Core Concept

The app solves the "what should we watch tonight" problem for couples who have different preferences. Instead of one person always compromising, the AI analyzes both taste profiles, finds the overlap zone, identifies tension points, and recommends movies that thread the needle.

## Architecture Decisions (Made During Brainstorming)

### Data Source: Pre-loaded Dataset
We evaluated three approaches: real API (TMDB), pre-loaded dataset, and hybrid. Chose **pre-loaded dataset** for the POC because:
- The goal is proving matching logic, not building a data pipeline
- A curated set keeps the demo self-contained and fast (no API latency/availability risk)
- The full dataset gets injected into the system prompt as context, constraining Claude to only recommend real movies
- Swapping in TMDB later is straightforward — the data shape stays the same

The current dataset is ~100 well-known films. A production version would need 500+ and should pull from TMDB.

### AI Engine: Claude (Anthropic API)
- Model: `claude-sonnet-4-20250514`
- The prompt engineering IS the product — structured profile input → carefully crafted system prompt → structured JSON output
- The system prompt enforces: only recommend from the dataset, return exact JSON schema, tone guidance for conversational output

### Approach: Structured Profiles + Prompt-Engineered Matching
We considered three approaches:
1. **Structured Profile → Prompt-Engineered Matching** ← chosen for POC
2. **Conversational Onboarding → Matching** — more natural but harder to build, harder to ensure comparable profiles
3. **Embedding-Based Similarity + AI Explanation** — more "real" rec engine, but complex for a POC

Key insight: the POC fakes the "feel" of Approach 3 (embedding-based) in the UX without the infrastructure. The taste map visualization shows per-person analysis, overlap zones, and tension points — the same output an embedding approach would produce — but it's generated by Claude's reasoning rather than vector math. If the concept validates, you swap in real embeddings and the UX barely changes.

## Feature Inventory (What the POC Does)

### Profile Input (per person)
- **Name** — used throughout the UI and in AI prompts
- **Comfort Movies** — searchable dropdown + quick-pick bubbles from curated popular films. Different quick-pick sets per profile to suggest different tastes
- **Watchlist** — same UI as comfort movies, different semantic meaning ("haven't seen, want to")
- **I Want** — unified tag vocabulary split into Moods & Tones (Cozy, Thrilling, Cerebral, Heavy, Quirky, etc.) and Genres (Horror, Sci-Fi, Fantasy, etc.). Supports custom freetext tags for anything not in the presets (e.g. "90s nostalgia")
- **Dealbreakers** — same unified tag vocabulary as I Want, same custom freetext support. Ensures someone can say "I want Sci-Fi" AND "no Heavy" using the same taxonomy
- **"[Partner] had a rough day" toggle** — an act of generosity, not a complaint. Opts the toggler into deprioritizing their own preferences (~65/35 weighting). If both toggle it, weights cancel out. This was a key design discussion — the framing deliberately avoids "who had the worst day" competition

### Session Mood
- **Tonight's Vibe** — same unified Moods & Genres tags
- **Freetext context** — "Long week, want to unwind together"
- **"Show us something new" toggle** — discovery mode that tells the AI to exclude comfort movies and watchlist titles from recommendations, using them only as taste signals

### Results (three output formats, toggleable tabs)
- **Taste Map** — per-person taste analysis cards (indigo for A, rose for B), overlap zone with shared vibes, tension points, and a legend showing preference weighting
- **Ranked List** — 5-7 movies with match scores (0-100), per-movie explanations referencing both profiles. Each card has ♥ (keep) and ✕ (remove) buttons for refinement
- **Conversational** — same recommendations in narrative form. Tone is warm and clear but NOT performatively familiar. This was explicitly iterated on — the first version was too "chummy" ("hear me out", "I got you") and felt uncanny valley. The current tone reads like a thoughtful reviewer, not a friend

### Refinement Loop
- Per-movie ♥/✕ ratings on the Ranked List tab
- Optional steering feedback textarea ("Something more lighthearted", "More animated films")
- Regenerate button that: keeps ♥'d movies, permanently excludes ✕'d movies, includes steering feedback, fills remaining slots with fresh picks
- Button label adapts contextually: "Show me different options →" / "Regenerate with ratings →" / "Regenerate with ratings + feedback →"
- Removed movies accumulate across rounds (never come back). Ratings reset per round so you can rate the new set fresh
- Start Over clears everything

## Prompt Design

The system prompt has this structure:

1. **Role & constraints** — "You are a movie recommendation engine for couples. Only recommend from [dataset]. Return only valid JSON."
2. **Discovery mode** (conditional) — exclude comfort/watchlist titles if toggled on
3. **Refinement instructions** (conditional) — keep these titles, exclude these titles, apply this feedback
4. **Tone guidance** — "Be warm and clear but not performatively familiar. Explain reasoning like a thoughtful reviewer, not a friend."
5. **Output schema** — exact JSON structure for tasteMap, recommendations, and conversational output

The user message includes both profiles, tonight's mood, freetext context, and preference weighting instructions.

The prompt forces taste analysis BEFORE recommendations (chain-of-thought effect) and explicitly asks for tension points to make the overlap analysis more honest.

## UI/UX Decisions & Iteration History

### Light theme, not dark
The initial build used a dark theme (`#0a0a12` background with white text). This was invisible in the Claude artifact container — the artifact chrome has its own background that clashed, making all text unreadable. Rebuilt with a light theme using inline styles (no Tailwind dependency) for reliable rendering.

### Inline styles throughout
Tailwind utility classes require the Tailwind compiler which isn't guaranteed in all environments. All styling is inline `style={{}}` objects for maximum portability. A production build would use a proper styling system.

### Components defined outside main function
An early version defined all subcomponents (MovieSearch, ProfileScreen, etc.) inside the main component body. This caused React to treat them as new component types on every render, unmounting/remounting inputs and dismissing the mobile keyboard after every keystroke. All components are now standalone functions at module level.

### Input font size ≥ 16px
Prevents iOS from auto-zooming into inputs on focus.

### Movie selection: search + quick-pick bubbles
The dataset has ~100 movies which is too many for a chip wall but too few for a real search experience. The solution: curated quick-pick bubbles (12 popular films per section, different per profile) with a search input below for finding anything else. Selected movies show as filled chips with ✕ to remove. The search has its own local state to avoid re-rendering the entire app on each keystroke.

### Toggle switch overflow fix
On mobile, the rough day toggle switch circle overflowed its track. Fixed with `minWidth: 44px` and `flexShrink: 0` on the track, plus proper flex layout with gap.

### Progress bar shows names, not "Profile A"
The step labels and page headers use the person's actual name ("Thayne's Taste Profile") instead of generic labels. Updates live as names are edited.

## Known Limitations / Next Steps

### Dataset
- Only ~100 movies. Production needs 500+ with rich metadata (genres, year, synopsis, streaming platforms, cast, runtime)
- No movie metadata in the current dataset — just titles. The AI infers genre/tone from its training knowledge. A production version should include structured metadata
- Quick-pick bubbles are hardcoded per-profile. A production version would personalize these based on popularity or user history

### Taste map visualization
- Currently text-based analysis cards. The original design included a taste spectrum visualization (a gradient bar showing where each person's preferences sit and where they overlap). This was in the first mockup but dropped during the rebuild. Worth revisiting with a proper data viz

### Streaming platform integration
- The original notes mention "look across multiple platforms." Not implemented. A production version should show where each recommended movie is available to stream

### Profile linking
- The original notes mention "link profiles." Currently both profiles are filled out on one device in sequence. A production version would need some way for each person to fill out their own profile on their own device — share link, QR code, or account system

### Persistent profiles
- Currently everything resets on page reload. Profiles should persist across sessions so you don't re-enter preferences every movie night

### The dataset-in-prompt approach won't scale
- At ~100 movies, injecting the full dataset into the system prompt is fine. At 500+ it'll eat context window. The production path is either: (a) a retrieval step that pre-filters candidates before the LLM ranks them, or (b) the Approach 3 embedding-based similarity to narrow candidates, with the LLM only reasoning over the top ~50

### Conversational tone
- The tone guidance in the prompt ("warm but not performatively familiar") works well but could benefit from few-shot examples in the system prompt to anchor the style more precisely
